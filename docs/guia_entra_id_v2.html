Guía práctica v2: Autenticación con Microsoft Entra ID para Pedidos360

Esta guía adapta el caso Pedidos360 (DSY1107, Examen Parcial 1) usando React en el frontend y AWS API Gateway + Lambda en el backend, en vez del stack original Angular + Spring Boot. La estructura y muchos de los conceptos siguen la guía de referencia de nuestro colega Cloud Native · Microsoft Entra ID, adaptada a nuestro stack y al caso del examen.

Versión 2 — corrige y completa la guía original con lo que aparece al hacer la integración completa de punta a punta con las versiones actuales de las librerías (@azure/msal-browser v3+, API Gateway HTTP API). Todo lo que agrega esta versión está marcado con v2.

Importante — versión del tenant. Usamos Microsoft Entra ID estándar (workforce tenant), no External ID/CIAM. External ID tiene un problema conocido con Azure for Students: al ser un recurso ARM, choca con la política de regiones permitidas de la suscripción estudiantil y falla la creación. Con Entra ID estándar se logra casi todo el objetivo de aprendizaje (PKCE, MSAL, JWT, roles, API Gateway) — la única diferencia es que los usuarios los crea el administrador del tenant en vez de auto-registrarse.

Qué cambió respecto a la v1

  • v2 Versión de token (v1 vs v2) explícita — se fija requestedAccessTokenVersion: 2 en la app Backend y se alinea el issuer y el audience del Authorizer con esa versión. Sin esto, el token es v1 y el Authorizer configurado con .../v2.0 devuelve 401. (Sección 7.)
  • v2 await msalInstance.initialize() — obligatorio en @azure/msal-browser v3 en adelante, antes de cualquier llamada MSAL. (Sección 6.)
  • v2 Fallback a acquireTokenRedirect — acquireTokenSilent también falla con timed_out (no solo interaction_required) cuando Chrome bloquea cookies de terceros. (Sección 6.)
  • v2 Guards de ruta explícitos (RequireAuth / RequireRole) con react-router-dom — en vez de un isAuthenticated ? ... : ... inline, cada página protegida cuelga de un guard nombrado y reusable, listo para las múltiples vistas de Pedidos360 (orders, catalog, admin…). (Sección 6b.)
  • v2 Sección de CORS para la HTTP API — el preflight OPTIONS es lo primero que rompe al conectar el frontend real. (Sección 7b.)
  • v2 Nota sobre MFA / Conditional Access — pedir un token para un recurso nuevo puede disparar un step-up de MFA. (Secciones 1 y 6.)
  • v2 Aclaración sobre la cuenta y el tenant — todo se crea con la cuenta de Azure for Students; un tenant de Entra ID estándar (a diferencia de External ID) no pide elegir suscripción; y hay que confirmar el cambio de directorio antes de registrar las apps. (Sección 1.)
  • v2 Tabla de errores comunes con síntoma → causa → solución. (Sección 9.)

1. Crear el tenant

Un tenant es una instancia aislada de Entra ID: un directorio propio con sus identidades, aplicaciones registradas y políticas de seguridad. Cada tenant tiene un Tenant ID único y un dominio <nombre>.onmicrosoft.com permanente.

Si ya crearon el tenant de Entra ID estándar en clases anteriores, pueden reutilizarlo — no hace falta uno nuevo por examen.

Todo esto se hace con su cuenta de Azure for Students. Entren a portal.azure.com con la misma cuenta con la que activaron la suscripción Azure for Students del curso — no con una cuenta personal ni con la cuenta institucional de otro servicio. El tenant de Entra ID que van a crear queda asociado a esa cuenta, y es desde adentro de ese tenant (una vez creado y con el directorio cambiado) que van a crear todos los recursos del resto de la guía: los dos App Registrations (secciones 3 y 4), los usuarios de prueba (sección 5), etc. Primero se crea el directorio; recién después, adentro de él, se crean los recursos.
1
Entren a portal.azure.com con su cuenta de Azure for Students.
2
Busquen "Id. de Microsoft Entra" en el Marketplace → Crear.
A diferencia de Entra External ID (que sí pide elegir Suscripción + Grupo de recursos, porque es un recurso ARM — y ahí es donde falla con Azure for Students), crear un tenant de Entra ID estándar no les va a pedir elegir una suscripción: el directorio no es un recurso que "vive dentro" de una suscripción, es independiente y gratuito. Lo único que importa es que estén logueados con la cuenta correcta en el paso 1.
3
Completen Nombre de inquilino (ej: "Pedidos360"), Nombre de dominio (será <nombre>.onmicrosoft.com, no se puede cambiar después) y País/región.
4
Esperen ~5 minutos. Al terminar, cambien de directorio (ícono de la cuenta, arriba a la derecha → Cambiar directorio / Switch directory) del directorio de Azure for Students al tenant nuevo, y configuren MFA con Microsoft Authenticator cuando se los pida.
El usuario que crea el tenant queda como Global Administrator de ese tenant: puede registrar aplicaciones, crear usuarios y asignar roles sin restricciones. En este tenant de práctica no hay problema en usarlo directamente. Confirmen que están parados en el tenant correcto revisando el nombre de directorio arriba a la derecha antes de seguir a la sección 3 — registrar la app en el directorio equivocado (el de Azure for Students en vez del tenant nuevo) es un error común en este paso.
v2 Sobre la MFA. Más adelante, cuando el frontend pida por primera vez un token para la API (un recurso distinto al login), Entra ID puede exigir una verificación extra (MFA / Conditional Access). Es step-up authentication: ya estabas autenticado, pero acceder a un recurso nuevo pide una prueba más fuerte. Es comportamiento esperado — se completa una vez y después la renovación silenciosa funciona sin volver a pedirla.

2. Por qué se registran DOS aplicaciones

Esta es la parte que más se presta a confusión, así que vamos directo al punto: en el tenant van a registrar dos "App Registrations" distintas, una para el frontend y otra para el backend. No es porque sean literalmente dos programas separados corriendo — es porque representan dos roles distintos dentro del modelo OAuth2, y Entra ID necesita que cada rol tenga su propia identidad registrada.

FRONTEND

Pedidos360-Frontend

Rol OAuth2: Cliente público (Public client)

Es quien pide el token en nombre del usuario que hace login. Corre en el navegador, no puede guardar secretos, así que usa el flujo Authorization Code + PKCE (sin client secret).

Se configura como: plataforma SPA, con Redirect URI apuntando a React (http://localhost:5173).

BACKEND

Pedidos360-API

Rol OAuth2: Recurso protegido (Resource server)

Es el dueño de los datos que el frontend quiere consumir. No pide tokens — los recibe y valida. Define qué permisos (scopes) existen sobre sus datos: orders.read, orders.write, etc.

Se configura como: app sin plataforma cliente, con Expose an API habilitado.

El flujo completo queda así: el usuario hace login desde Pedidos360-Frontend, que le pide a Entra ID un token con permiso para usar la API de Pedidos360-API. Entra ID entrega ese token solo si el frontend tiene API permissions concedidos sobre esos scopes del backend. El backend (vía API Gateway) recibe el token y valida que el audience del token corresponda exactamente a esta API — es decir, que el token fue emitido específicamente para hablar con ella, no con cualquier otra cosa del tenant.

Analogía rápida: Pedidos360-Frontend es como la persona que pide una llave en portería. Pedidos360-API es la puerta con la cerradura. La llave (token) solo sirve porque fue cortada específicamente para esa cerradura (audience = identidad del backend) — no abre cualquier puerta del edificio.

3. Registrar la app Backend (Pedidos360-API)

Se registra primero porque el frontend necesita referenciarla al pedir permisos.

1
Registros de aplicaciones → Nuevo registro. Nombre: Pedidos360-API. Tipo de cuenta: Solo este directorio organizativo. Sin Redirect URI (no la necesita, no hace login).
2
Copien el Application (client) ID — es la identidad del backend, la van a usar en el audience del JWT Authorizer.
3
Exponer una API → Agregar junto al URI de identificador de aplicación. Déjenlo con el valor por defecto: api://<client-id>. (Aunque después usemos tokens v2, este URI debe existir para poder definir scopes.)
4
+ Agregar un ámbito por cada permiso que su API necesite exponer, nombrados por dominio: 
orders.read    → Ver pedidos
orders.write   → Crear/actualizar pedidos
catalog.read   → Ver catálogo
catalog.write  → Administrar catálogo
Para cada uno: quién puede dar consentimiento (recomendado: Admins y usuarios para simplificar el examen), nombre visible y descripción.
5
App roles (menú lateral) → creen los roles del negocio: Admin, Operador y Cliente. Tipo permitido: Users/Groups. Estos son los roles que después van a aparecer dentro del token como claim roles.
6
v2 Manifest → requestedAccessTokenVersion. Abran Manifest (pestaña "Microsoft Graph App Manifest"), busquen el objeto "api" y cambien: 
"api": {
    ...
    "requestedAccessTokenVersion": 2   // estaba null
}
Guarden. Esto hace que todos los access tokens emitidos para esta API sean v2: iss con /v2.0 y aud = el client ID pelado (sin api://). Ver por qué en la sección 7.

4. Registrar la app Frontend (Pedidos360-Frontend)

1
Nuevo registro. Nombre: Pedidos360-Frontend. Tipo de cuenta: Solo este directorio organizativo.
2
Authentication → + Add a platform → Single-page application (SPA). Redirect URI: http://localhost:5173 (Vite).
v2 Tiene que ser la plataforma SPA, no "Web". MSAL browser usa Authorization Code + PKCE y necesita el tipo SPA; con "Web" el login falla o da errores de CORS al canjear el código.
3
Copien el Application (client) ID y el Directory (tenant) ID desde Overview — van directo al .env de React. Ojo: es el client ID de esta app (Frontend), no el del Backend.
4
API permissions → Add a permission → My APIs → Pedidos360-API. Marquen los scopes que el frontend va a usar (ej: orders.read, orders.write).
5
Grant admin consent para ese tenant — evita que cada usuario tenga que aprobar el permiso manualmente la primera vez que inicia sesión.
Si se les olvida el Grant admin consent, el login funciona pero acquireTokenSilent falla al pedir el token de la API pidiendo interacción — es el error más común en este paso.

5. Asignar roles a los usuarios de prueba

Como estamos en Entra ID estándar (no External ID), los usuarios no se auto-registran — el administrador del tenant los crea.

1
Usuarios → Nuevo usuario → creen 2-3 cuentas de prueba (ej: admin@<tenant>.onmicrosoft.com, operador@..., cliente@...).
2
Vayan a Enterprise applications → Pedidos360-API → Users and groups → Add user/group, y asignen a cada cuenta uno de los App Roles existentes: Admin, Operador o Cliente.
3
Cuando ese usuario inicie sesión desde el frontend, el access_token traerá el claim "roles": ["Operador"] (por ejemplo) — eso es lo que después el backend usa para autorizar.
Diferencia scopes vs roles. En el access token verán dos claims relacionados pero distintos: scp (los scopes delegados que el cliente pidió y tiene concedidos, ej. "orders.read orders.write") y roles (los App Roles asignados al usuario). Para "solo Admin puede editar el catálogo" se usa roles. Para "este cliente solo pidió permiso de lectura" se usa scp.

La integración sigue la guía de referencia — los cambios reales de esta v2 son tres: llamar a initialize(), pedir el scope de nuestra API (no User.Read de Graph), y tener un fallback a redirect cuando el token silencioso no se puede renovar.

v2 src/useApi.ts — interceptor con fallback a redirect

import { useMsal } from "@azure/msal-react";
import { InteractionRequiredAuthError, BrowserAuthError } from "@azure/msal-browser";
import { apiRequest } from "./authConfig";

export function useApi() {
  const { instance, accounts } = useMsal();

  const fetchWithToken = async (path: string, init: RequestInit = {}) => {
    const account = accounts[0] || instance.getActiveAccount();
    if (!account) throw new Error("No hay una cuenta activa");

    let token: string;
    try {
      const r = await instance.acquireTokenSilent({ ...apiRequest, account });
      token = r.accessToken;
    } catch (e) {
      // interaction_required / consent_required  -> falta consentimiento o MFA
      // timed_out / monitor_window_timeout       -> el iframe silencioso no completa
      //   (Chrome bloquea cookies de terceros para login.microsoftonline.com)
      const needsInteraction =
        e instanceof InteractionRequiredAuthError ||
        (e instanceof BrowserAuthError &&
         ["timed_out", "monitor_window_timeout"].includes(e.errorCode));
      if (needsInteraction) {
        await instance.acquireTokenRedirect({ ...apiRequest, account }); // navega y vuelve
      }
      throw e;
    }

    return fetch(`${import.meta.env.VITE_API_BASE_URL}${path}`, {
      ...init,
      headers: { ...init.headers, Authorization: `Bearer ${token}` },
    });
  };

  return { fetchWithToken };
}

El resto (App.tsx con loginRedirect/logoutRedirect) sigue el patrón de la guía de referencia. La llamada real:

const res = await fetchWithToken("/pedidos");   // -> GET https://<api-id>.execute-api.../pedidos

6b. v2 Guards de ruta: RequireAuth y RequireRole

Pedidos360 no es una sola pantalla — va a tener vistas para orders, catalog, y una sección de administración. Eso sigue siendo una SPA (sigue siendo un cliente con enrutamiento en el navegador, sin recargar página) — lo que cambia es que ahora hay varias rutas, y cada una necesita decidir "¿puede este usuario ver esto?" antes de renderizar. Esa decisión es un guard, el mismo concepto que un CanActivate de Angular Router.

La forma correcta de aplicarlo con react-router-dom es como layout route: un componente guard que envuelve un <Outlet/>, y todas las rutas protegidas cuelgan de él. Así el guard se escribe una vez y no se repite un if (isAuthenticated) en cada página nueva.

AUTENTICACIÓN

RequireAuth

¿Hay sesión activa? Si no, redirige sola al login — no hace falta un botón en cada página protegida.

AUTORIZACIÓN

RequireRole

Con sesión ya confirmada: ¿el usuario tiene el App Role que esta sección exige? Si no, muestra un mensaje — no navega a ningún lado.

src/RequireAuth.tsx

import { Outlet } from "react-router-dom";
import { MsalAuthenticationTemplate } from "@azure/msal-react";
import { InteractionType } from "@azure/msal-browser";
import { loginRequest } from "./authConfig";

export function RequireAuth() {
  return (
    <MsalAuthenticationTemplate
      interactionType={InteractionType.Redirect}
      authenticationRequest={loginRequest}
      loadingComponent={() => <p>Redirigiendo a inicio de sesión…</p>}
    >
      {/* Todo lo que cuelgue de esta ruta en App.tsx se renderiza acá */}
      <Outlet />
    </MsalAuthenticationTemplate>
  );
}

MsalAuthenticationTemplate es el guard de autenticación que ya trae MSAL React — usarlo en vez de un ternario a mano también enseña que esto es un concepto de la librería, no un if/else improvisado.

src/RequireRole.tsx

import { useEffect, useState } from "react";
import { Outlet } from "react-router-dom";
import { useMsal } from "@azure/msal-react";
import { acquireApiToken } from "./api/client"; // el mismo helper de la sección 6
import { decodeJwt } from "./lib/jwt";

export function RequireRole({ role }: { role: string }) {
  const { instance, accounts } = useMsal();
  const account = accounts[0] ?? instance.getActiveAccount();
  const [status, setStatus] = useState<"loading" | "allowed" | "denied">("loading");

  useEffect(() => {
    if (!account) return;
    let cancelled = false;
    acquireApiToken(instance, account)
      .then((token) => {
        if (cancelled) return;
        const roles = decodeJwt(token)?.roles ?? [];
        setStatus(roles.includes(role) ? "allowed" : "denied");
      })
      .catch(() => !cancelled && setStatus("denied"));
    return () => { cancelled = true; };
  }, [instance, account, role]);

  if (!account || status === "loading") return <p>Verificando permisos…</p>;
  if (status === "denied") return <p>Requiere el rol {role}.</p>;
  return <Outlet />;
}
Por qué no accounts[0].idTokenClaims.roles. El claim roles de los App Roles vive en el access token de la API (el que se pide con apiRequest, audience = tu backend) — no en el ID token del login, cuya audience es la propia app Frontend. Por eso RequireRole llama a acquireApiToken, el mismo helper que ya usa el interceptor: así el guard revisa exactamente el mismo claim que después va a revisar la Lambda, sin una fuente de verdad paralela que se pueda desincronizar.
Un guard de rol es UX, no seguridad: solo evita que el botón aparezca. Un usuario podría llamar la API directamente sin pasar por React. La Lambda tiene que volver a validar el rol con el mismo claim (sección 8) — el guard nunca reemplaza esa validación en el backend.

Armándolo en App.tsx

<Routes>
  <Route path="/" element={<Landing />} />

  {/* Guard de AUTENTICACIÓN: agrupa las rutas que exigen sesión */}
  <Route element={<RequireAuth />}>
    <Route path="/dashboard" element={<Dashboard />} />
    <Route element={<RequireRole roles={["Admin", "Operador"]} />}>
      <Route path="/catalogo" element={<Catalogo />} />
    </Route>
    <Route element={<RequireRole roles={["Admin", "Operador", "Cliente"]} />}>
      <Route path="/pedidos" element={<Pedidos />} />
    </Route>
  </Route>
</Routes>

Las rutas del frontend son /dashboard, /catalogo y /pedidos. El dashboard requiere sesión; el catálogo permite Admin y Operador, y pedidos permite Admin, Operador y Cliente.

El frontend Pedidos360 implementa RequireAuth para rutas privadas y RequireRole para catálogo y pedidos. La comprobación usa el claim roles del access token de Pedidos360-API y es un control de experiencia de usuario; la seguridad real debe volver a aplicarse en API Gateway y el backend.

7. Backend: API Gateway + JWT Authorizer

A diferencia del ejercicio con Spring Security (donde había que validar el JWT a mano), API Gateway HTTP API valida el token antes de que la petición llegue a la Lambda — no se escribe código de validación de firma, issuer ni audience.

1
Cuando se incorpore el backend, creen una HTTP API con rutas como GET /pedidos, GET /pedidos/{id}, POST /pedidos, PUT /pedidos/{id}/estado, GET /catalogo y PUT /catalogo/{id}, cada una integrada al servicio correspondiente.
2
Authorization → Manage authorizers → Create → JWT. Configuren según la versión de token (ver tabla abajo). Con requestedAccessTokenVersion: 2 en la app Backend (sección 3, paso 6): 
Issuer URL:  https://login.microsoftonline.com/<TENANT_ID>/v2.0
Audience:    <client-id del Backend>      (GUID pelado, SIN api://)
3
Adjunten ese Authorizer a cada ruta protegida y agreguen la scope requerida si quieren que el Authorizer también filtre por permiso (ej. orders.read). API Gateway ahora responde 401 antes de invocar la Lambda ante cualquier request sin token, con firma incorrecta, issuer distinto o audience distinto.
v2 La trampa v1 / v2 (causa #1 de 401). El iss y el aud del token dependen de la versión que emita la app Backend. Tienen que ser un conjunto coherente: no se puede mezclar el issuer de v2 con el audience estilo v1.
v1 (por defecto, requestedAccessTokenVersion: null)v2 (requestedAccessTokenVersion: 2) — recomendado
iss del tokenhttps://sts.windows.net/<TENANT_ID>/ (con / final)https://login.microsoftonline.com/<TENANT_ID>/v2.0
aud del tokenapi://<backend-client-id><backend-client-id> (GUID pelado)
Authorizer · Issuer URLhttps://sts.windows.net/<TENANT_ID>/https://login.microsoftonline.com/<TENANT_ID>/v2.0
Authorizer · Audienceapi://<backend-client-id><backend-client-id>

Recomendación: v2. Es el estándar OIDC actual, el issuer coincide con el patrón .well-known/openid-configuration que ya vieron en la actividad de decodificar JWT, y si algún día migran a External ID (que solo emite v2) la configuración del Authorizer no cambia. Para elegir v2, hagan el paso 6 de la sección 3.

Para ver qué trae realmente su token: cópienlo desde la consola del navegador y péguenlo en jwt.ms. Verifiquen aud, iss, scp, roles y exp antes de pelear con el Authorizer.

7b. v2 CORS en la HTTP API

Apenas el frontend real (en http://localhost:5173) llama a la API, el navegador manda primero una petición preflight OPTIONS — porque la llamada lleva el header Authorization, lo que la vuelve una petición "no simple". Si API Gateway no responde ese preflight con las cabeceras CORS, verán en consola:

Access to fetch at '...execute-api.../pedidos' from origin 'http://localhost:5173'
has been blocked by CORS policy: Response to preflight request doesn't pass
access control check: No 'Access-Control-Allow-Origin' header is present...

Esto es independiente de la autenticación — el preflight OPTIONS ni siquiera lleva token. Se arregla en la consola de API Gateway:

1
API Gateway → su HTTP API → CORS → Configure.
2
Access-Control-Allow-Originhttp://localhost:5173
Access-Control-Allow-Headersauthorization, content-type
Access-Control-Allow-MethodsGET, POST, PUT, DELETE, OPTIONS
Access-Control-Max-Age300
3
Guarden. La HTTP API responde el OPTIONS por sí sola y no ejecuta el Authorizer en el preflight, así que no hace falta una ruta OPTIONS aparte.

Por CLI:

aws apigatewayv2 update-api --api-id <API_ID> --region us-east-1 \
  --cors-configuration AllowOrigins="http://localhost:5173",AllowMethods="GET,POST,PUT,DELETE,OPTIONS",AllowHeaders="authorization,content-type",MaxAge=300
Si su integración es Lambda proxy, la respuesta real (200) también necesita el header Access-Control-Allow-Origin. En HTTP API se agrega solo cuando CORS está configurado; en REST API la Lambda lo debe devolver en headers.

8. Lambda: autorización por rol

El JWT Authorizer valida que el token sea auténtico, pero no sabe de reglas de negocio como "solo Admin puede editar catálogo". Eso se revisa dentro de la Lambda, leyendo el claim roles (o scp) que ya viene validado en el token.

// catalog-update/index.mjs
export const handler = async (event) => {
  // API Gateway ya validó firma/issuer/audience. Acá solo leemos claims.
  const claims = event.requestContext.authorizer.jwt.claims;

  // OJO: en HTTP API + JWT Authorizer, los claims que en el JWT original son
  // ARRAY (como "roles") llegan achatados a STRING (no como array JSON), y
  // "scp" siempre fue string separado por espacios. El separador exacto que
  // usa API Gateway para achatar arrays puede ser espacio o coma según el
  // claim — hagan console.log(JSON.stringify(claims)) una vez y ajusten
  // el split si hace falta. Este regex cubre ambos casos:
  const split = (v) => (v || "").split(/[\s,]+/).filter(Boolean);
  const roles = split(claims.roles);
  const scopes = split(claims.scp);

  if (!roles.includes("Admin")) {
    return { statusCode: 403, body: JSON.stringify({ error: "Requiere rol Admin" }) };
  }

  // ... lógica de negocio (actualizar producto) ...
  return { statusCode: 200, body: JSON.stringify({ ok: true }) };
};
El claim de roles en API Gateway HTTP API con JWT Authorizer llega dentro de event.requestContext.authorizer.jwt.claims, no en event.headers. Y llega como string (achatado), no como array. Es el error más común al conectar por primera vez — hagan console.log(JSON.stringify(event.requestContext.authorizer)) si el claim no aparece donde esperan o el .split() no separa como esperaban.

9. v2 Errores comunes

SíntomaCausaSolución
AADSTS500113: No reply address is registered La Redirect URI no está registrada, está como plataforma "Web" en vez de "SPA", o el VITE_AZURE_CLIENT_ID apunta a la otra app. En la app Frontend: Authentication → Add a platform → SPA → http://localhost:5173. Verificar que el client ID del .env sea el de la app Frontend.
BrowserAuthError: uninitialized_public_client_application No se llamó await msalInstance.initialize() antes de usar MSAL (obligatorio en msal-browser v3+). Inicializar antes de renderizar (sección 6).
Pantalla en blanco justo después del login MSAL está procesando el #code=... del redirect. Normal por unos milisegundos. Si persiste, revisar consola por errores.
BrowserAuthError: timed_out / monitor_window_timeout al pedir el token de la API El iframe silencioso no puede completar: Chrome bloquea cookies de terceros para login.microsoftonline.com, o falta el admin consent. Fallback a acquireTokenRedirect (sección 6). Confirmar Grant admin consent en la app Frontend.
Prompt de MFA al pedir el token de la API (no en el login) Conditional Access hace step-up al acceder por primera vez a un recurso protegido nuevo. Completar la MFA una vez. Después la renovación silenciosa funciona hasta que expira el claim.
CORS policy: No 'Access-Control-Allow-Origin' header API Gateway no responde el preflight OPTIONS. Configurar CORS en la HTTP API (sección 7b).
401 desde API Gateway (nunca llega a la Lambda) iss o aud del token no coinciden con el Authorizer. Típico: mezclar v1/v2, o falta la / final del issuer v1. Pegar el token en jwt.ms, comparar iss/aud con el Authorizer usando la tabla de la sección 7.
403 desde la Lambda El token es válido pero el usuario no tiene el rol/scope requerido. Asignar el App Role al usuario (sección 5). Revisar claims.roles / claims.scp (llegan como string, no array).
npm install → EUNSUPPORTEDPROTOCOL "workspace:" El repo base usa pnpm (tiene pnpm-lock.yaml). corepack pnpm install.
